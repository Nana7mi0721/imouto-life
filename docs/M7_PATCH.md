# M7 补丁文件格式（记录级二进制 mod 补丁）

本文件描述 mod 目录下 `patches/` 目录里 `*.patch` 文件的格式。它面向 mod 作者：用最小、可复核的方式修改解包数据，而不必重打包 `.wolf`。

补丁在数据加载时应用，支持两类操作：

- **字节区间补丁**：对任意数据文件按偏移替换一段等长字节，写入前会核对原字节。
- **记录补丁**：按 类型 / 行 / 列 修改数据库（`DataBase.dat`、`CDataBase.dat`）中的一个单元格，支持数值与字符串；字符串变长由序列化器自动处理。

> 所有补丁在内存中生效，磁盘上的原始文件不会被改写。

## 1. 目录结构

补丁放在 mod 叠加目录（`Game::with_overlays` 传入的目录）下的 `patches/` 子目录：

```text
<mod 目录>/
├── mod.ini
├── BasicData/            # 可选：直接覆盖的数据文件（既有机制）
│   └── DataBase.dat
└── patches/              # 本文件描述的补丁
    ├── 01-window.patch
    └── 02-database.patch
```

- 只加载扩展名为 `.patch`（大小写不敏感）的普通文件。
- 同一目录内按文件名排序加载；多个 mod 叠加时按叠加顺序（后者在后）依次追加。
- 没有 `patches/` 目录的 mod 不受影响。

## 2. 文件语法

每个 `.patch` 文件描述**一个**补丁，逐行写 `键 = 值`：

- 空行、以 `#` 或 `//` 开头的行是注释。
- 键名大小写不敏感；值两端空白会被去掉。
- 同一个文件里重复出现的键，以**第一次**出现为准。
- 含 `offset` / `expect` / `replace` 任一键的文件按**字节补丁**解析；否则按**记录补丁**解析。

### 2.1 字节区间补丁

| 键 | 必填 | 含义 |
| --- | --- | --- |
| `file` | 是 | 目标文件，按文件名或路径后缀匹配 |
| `offset` | 是 | 起始偏移（十进制，或 `0x` 前缀十六进制） |
| `expect` | 是 | 文件在该处当前应有的字节（十六进制，空格或逗号分隔） |
| `replace` | 是 | 写入的字节；长度必须与 `expect` 相同 |

示例：

```text
# 把 SystemFile/WindowBase.png 偏移 0x10 起的 4 字节换掉
file    = SystemFile/WindowBase.png
offset  = 0x10
expect  = 7A 2B 3C 4D
replace = 00 11 22 33
```

规则：

- **先校验后写入**：所有匹配的字节补丁会先全部核对 `expect`，任何一个不匹配就报错并且**一个字节都不写**。
- `expect` 与 `replace` 必须等长；字节补丁不会让文件变长或变短。
- 区间必须落在文件范围内；越界会报错。
- `file` 匹配忽略路径分隔符与大小写，可用文件名（`WindowBase.png`）或路径后缀（`SystemFile/WindowBase.png`）。

### 2.2 记录补丁

| 键 | 必填 | 含义 |
| --- | --- | --- |
| `file` | 是 | 目标库：`DataBase.dat` 或 `CDataBase.dat` |
| `type` | 是 | 类型索引（从 0 开始） |
| `row` | 是 | 行索引（从 0 开始） |
| `column` | 二选一 | 列索引（从 0 开始） |
| `column_name` | 二选一 | 列名（来自对应 `.project` 伴随文件的字段名） |
| `number` | 二选一 | 写入的 32 位有符号整数 |
| `text` | 二选一 | 写入的字符串 |

示例（按列索引，写数值）：

```text
file   = CDataBase.dat
type   = 18
row    = 97
column = 0
number = 32
```

示例（按列名，写字符串）：

```text
file        = CDataBase.dat
type        = 18
row         = 0
column_name = ウィンドウ画像
text        = SystemFile/WindowBase.png
```

规则：

- `column` 与 `column_name` 只能有一个；`number` 与 `text` 只能有一个。
- `column_name` 依赖对应库的 `.project` 字段名表；找不到该名字会报错。
- 写入的字符串可以比原值更长或更短：序列化器会重写长度字段。
- 列的数值/字符串种类必须与值匹配（数值列只接受 `number`，字符串列只接受 `text`）。
- 记录补丁在数据库解析、项目名应用、引擎默认值填充**之后**执行，因此可以覆盖引擎自身写入的单元格。

## 3. 错误处理

- 补丁文件语法错误、读取失败或字节校验失败时，游戏**不会**崩溃：错误会写到标准错误（`eprintln!`），对应补丁被跳过，其余补丁照常应用。
- 字节补丁的校验是"全有或全无"：只要有匹配的补丁校验失败，该文件本次不做任何字节替换。
- 记录补丁遇到不存在的类型/行/列时记录错误并停止应用剩余的记录补丁。

## 4. 开发者验证

- 单元测试（补丁解析、字节校验、记录写入）：`cargo test -q -p wolf-game --lib patch`
- 端到端测试（数据库与资产加载时应用补丁）：`cargo test -q -p wolf-game --test m7_patch`
- 数据库序列化逐字节一致性（需解包数据）：`WOLF_DATA_ROOT=work/Data cargo test -q -p wolf-format --test database_serializer`

## 5. 设计说明

- **为什么字节补丁要等长**：任意文件（含图片）无法安全地"插入"字节而不破坏其后结构，等长替换是唯一通用且可校验的做法。需要改变数据库字符串长度时，用记录补丁——它由序列化器统一处理长度字段。
- **为什么记录补丁在解析后应用**：数据库是结构化数据，按 类型/行/列 直接定位比按文件偏移稳定，且不受字段表变化影响。
- **编码**：未被补丁改动的字符串按原始编码块原样回写（本作多为 CP932，汉化版可能为 GBK）；被记录补丁改写的字符串按 UTF-8 重新编码。因此"读入 → 不改 → 写回"可逐字节还原，而改动过的字符串以 UTF-8 落盘。
