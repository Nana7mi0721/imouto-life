## 1 §3-8 coordinate_scale 的取整方式

### 1.1 原版行为（A 级）

坐标倍率**不在本地码里算**，而是由数据（CommonEvent）算完写进 DB：

`work/out/layout_metrics/ce48.txt:17-18`（CE48 pc30/31）：

```text
op=121 ints=[1600025, 9000116, 32, 12288]     # v25 = Sys116 / 32
op=121 ints=[1600026, 9000117, 24, 12288]     # v26 = Sys117 / 24
```

- `9000116`/`9000117` = Sys116/Sys117（magic 前缀 `0x9000000 + index` 就是系统变量）。
- op121 第 4 个 int 是 `bits`，`(bits>>12)&0xF` 选二元算子；`12288 = 0x3000 -> 3 = 整除`
  （`crates/wolf-vm/src/exec.rs:1540-1560` `binary_op(0x3) = a.wrapping_div(b)`，注释里正好
  拿 `Sys116/32` 举例）。`wrapping_div` == x86 `idiv` == **向零截断**，不是 floor，
  也不是 round。
- Sys116/Sys117 就是**逻辑（未乘 DAT_0084b248）屏幕宽高**：
  `work/out/re_all/all/0043f460_FUN_0043f460.c:451` `local_2c = DAT_0084b230 / DAT_0084b248;`
  （case 0x74）、`:454` `DAT_0084b234 / DAT_0084b248`（case 0x75）。
  而 `DAT_0084b230 = *DAT_00a16718 * DAT_0084b248`
  （`00469820_FUN_00469820.c:443-444`），所以 getter 返回的就是 Game.dat 里的原始宽高
  （1024/576；320x240 时也返回 320/240，因为乘过又除回去了）。

**同一函数里还有第二种分支（A 级）**：三种标准分辨率被**硬编码**成固定倍率，不再做除法：

| CE48 行 | 写入 | 值 | 对应分辨率 |
|---|---|---|---|
| `ce48.txt:42-49`（pc58..63） | CData(18,97)=10、18,98=10、18,5=10、18,6=8、18,7=6、Sys8=12 | 倍率 10 | 320x240 |
| `ce48.txt:52-59`（pc69..74） | 97=20、98=20、5=20、6=16、7=12、Sys8=24 | 倍率 20 | 640x480 |
| `ce48.txt:62-68`（pc80..85） | 97=25、98=25、5=26、6=20、7=15、Sys8=30 | 倍率 25 | 800x600 |

三档数值与 `w/32`、`h/24` 完全吻合（320/32=10、640/32=20、800/32=25；240/24=10、
480/24=20、600/24=25），说明硬编码只是"预计算缓存"，语义仍是整除。

B 级旁证：本地码里正有一个"分辨率档位"getter `FUN_0043f460` case 0x54
（`0043f460.c:351-357`）对 320x240 / 640x480 / 800x600 返回 0/1/2，其它返回 -1，正好对应
CE48 的三档分支 + 自动计算分支（分支开关是 `Sys84`：`ce48.txt:40`）。

### 1.2 仓内实现

- `crates/wolf-game/src/db.rs:159-165`：`(w/32).max(1)`、`(h/24).max(1)`，u32 整除
  → **与原版等价**（`.max(1)` 是仓内防御，原版脚本无钳制；只有屏宽 < 32 才可能差，不可达）。
- `crates/wolf-game/src/message.rs:97-102`：`(screen_w/32.0).max(1.0)`，**f32 除法** →
  与原版不同。
- 仓内自测值：`db.rs:1002-1005`、`message.rs:668-670`（1024x576 -> (32,24)、
  1280x720 -> (40,30)），这两个都能整除，所以测不出差异。

### 1.3 差异（B 级推算）

原版先整除再使用；仓内 message 侧用浮点。以 1200x700 为例：

| | rateX | rateY | 备注 |
|---|---|---|---|
| 原版 | 1200/32 = **37** | 700/24 = **29** | 向零截断 |
| 仓内 message.rs | 37.5 | 29.1667 | 浮点 |
| default_origin | 原版 (74, 17*29+29/10 = **495**) | 仓内 round(75), round(495.83+2) = **498** | 差 3 px |

即使 db 侧 CData(18,97|98) 与原版一致，只要文本原点走 message.rs 的浮点公式，非 32/24 整倍数
分辨率下原点就会漂。**建议改法**：message.rs 的 coordinate_scale/default_origin 改成整数运算
（`(h as i32 / 24).max(1)`），再沿用 §2 的公式即可逐位对齐。

## 2 §3-9 default_origin 的 trunc(rateY/10)

### 2.1 原版行为（A 级）——公式确实是原版的

`work/out/layout_metrics/ce63.txt:25-27`（CE63 pc44..46，CE63 = メッセージウィンドウ）：

```text
op=121 ints=[9000001, 2, 1600088, 8192]      # Sys1  = 2  * self88
op=121 ints=[9000002, 17, 1600089, 8192]     # Sys2  = 17 * self89
op=121 ints=[9000002, 1600089, 10, 12544]    # Sys2 += self89 / 10
```

- `8192 = 0x2000 -> 2 = 乘`；`12544 = 0x3100`：复合算子 `0x100 = 加`，二元算子
  `3 = 整除`。
- `self88`/`self89` 就是 rateX/rateY（**不是 x10**）——同文件 `ce63.txt:20-21`：
  `v42 = self88 * 32`、`v43 = self89 * 24`，这两个变量在 `selfnames` 里叫
  「画面サイズX/Y」，1024 = 32*32、576 = 24*24 反解得 self88=32、self89=24。
- 于是 **Sys1 = 2*rateX = 64，Sys2 = 17*rateY + rateY/10 = 408 + 2 = 410**，与实机/仓内
  `Sys1/Sys2=(64,410)` 完全一致；`rateY/10` 项确认存在且是**整除**（24/10=2）。

### 2.2 仓内实现

`crates/wolf-game/src/message.rs:111-120`：

```rust
(2.0 * rate_x).round(),
(17.0 * rate_y + (rate_y / 10.0).trunc()).round(),
```

公式结构一致（整数屏下 `.round()` 无效）。**问题同 §1：rate_x/rate_y 是浮点**，所以
"先乘 17 再加 trunc(rate/10)" 只在 24 的整倍数下等于原版。原版也没有 `.max(1)`。

另有脚本侧细节（不是引擎行为）：`ce63.txt:8-9` 对 CData(18,97|98) 做
`+= self88/self89`（追加一次 rate），所以这两个 DB 单元在 CE63 跑过之后 = 2*rateX / 2*rateY。

### 2.3 结论

- `trunc(rateY/10)` **是原版公式**（不是仓内臆造），A 级证据在 CE63 pc46。
- 要改的是**上游 rate 的数值类型**（整数），不是这一项本身。
- `docs/ENGINE_BEHAVIOR.md:66,73` 的「[公式推断]」可以升级为「已核对（数据侧）」。

## 4 §3-2 极小盒退化

### 4.1 原版行为（A 级：没有钳制/折半）

同一段九宫格代码里，中段目标宽度就是 `right - corner`，**没有任何 min(corner, w/2) 钳制**：

`00488310_FUN_00488310.c:1071-1084`：

```c
FUN_0051f060((local_18 - P1(0x1c0))*s, ...)                       /* 右列 x = right - 3 */
FUN_0051f060((local_18 - P1(0x1c0))*s, (local_14 - P1(0x1c8))*s, ...) /* 右下角 */
```

- 盒宽 < 2*帧厚时，中列的 x2 会小于 x1（**反向矩形**），中段宽度为 0 或负。
- 角片始终按帧厚原尺寸画，不会"折半"，也不会被剪进盒内。
- 结论：**原版没有 MIN_BOX 语义、也没有角折半**；退化交给 DxLib 的 blit 裁剪
  （C 级：DxLib 对 x2<x1 的实际处理未实测，因为不能跑原版）。

### 4.2 仓内实现与差异

- `window.rs:37 MIN_BOX=2` 是**仓内哨兵**（"没有显式 box"）；原版没有这个常量。
- `window.rs:78-90` 的 `(cw as f32).min(w/2.0)` 角折半是**仓内安全实现**，与原版不同。
  视觉上可能一样（都看不到角），但要逐像素对齐就得保留固定角 + 反向中段；建议去掉
  `.min(w/2)`，让 `nine_slice` 现有的 `dw<=0` 跳过逻辑吞掉反向片。

## 5 §3-6 选择面板越界回退

### 5.1 已确认（A 级）的原版输入

- **面板锚点 = Sys3/Sys4**，由 CE63 写死：`ce63.txt:23-24` `Sys3 = 16*rateX`、
  `Sys4 = 8*rateY` → 1024x576 时 (512, 192)。Sys5/Sys6 是光标相对偏移（`message.rs`
  注释亦同），与面板位置无关。
- **游戏确实会给面板喂屏外坐标**：CE42「オリジナルタイトル画面Ａ」pc25/pc26：
  `Sys3 = -1000`、`Sys4 = -1000`（`scan_sys.py` 输出第 1-2 行）。
  旧注释里的 "(512,1000)" 是错的。
- 手册语义：`-1` = "默认位置"（WOLF 手册对窗口坐标的约定）。数据里用的是 -1000，不是 -1。

### 5.2 结论（B 级）：原版**不做居中回退**

1. 原版标题画面没有引擎绘制的灰色选择面板（docs/REFERENCE.md 的标题截图）。
2. CE42 把 Sys3/Sys4 设成 -1000 而游戏照常运行、菜单靠脚本自己的图片按钮 —— 若引擎会把越界
   坐标"居中回退"，标题上必然出现引擎面板，与实机不符。
3. 检查过的引擎绘制/取参路径（`00488310` 九宫格、`00487580` 取参数、`0043f460`
   配置 getter）里**没有任何窗口坐标的 -1/越界判断**；唯一坐标夹取在
   `0042c8b0_FUN_0042c8b0.c:146-220`，但那是**鼠标坐标**夹到
   `[0,DAT_0084b230] x [0,DAT_0084b234]`（`DAT_0084b248==2` 时再 /2），与面板位置无关。
4. 因此原版最可能「**按 Sys3/Sys4 原样绘制、越界即被屏幕裁剪**」：既不是"完全越界才居中"，
   也不是"部分越界即回退/贴边夹取"。

### 5.3 仓内差异

`choice.rs:180-214` 在"完全屏外"时居中回退。判断条件
`rect[0] < W && rect[1] < H && rect[0]+w > 0 && rect[1]+h > 0` 是**矩形相交**判据：

- 原版：(-1000,-1000) → 面板画到屏外 → 玩家看不到（游戏正是利用这点）。
- 仓内：同一坐标 → 居中面板。**这是可见的行为差异**：哪个事件想隐藏引擎面板，仓内会显示出来。

建议（需 task-owner 决定）：**先读 §5.4-5.6**——已定位到 102 的引擎实现，结论比本节的 B 级更强：
原版锚点根本不用 Sys3/Sys4，回退也不存在。改法应为"删掉居中回退 + 按原版对象字段落点"，
但 §5.6 第 2 条的矛盾（标题看不到面板）必须先解决，否则会把隐藏菜单变成可见菜单。

*(int *)(obj + 0x18c) = *last + 0x1a + *last2;

→ **没有任何"最大宽"钳制、没有截断、没有换行**；选项有多宽面板就有多宽（+26 px），因此可以超出
屏宽。这与仓内 `choice.rs:112` 的 `(widest + marker + 2*PADDING + SLACK)` 在"无上限"
这一点上一致，但常数完全不同（原版 +26，仓内 +30(marker)+28(padding)+4(slack)=+62，且另有
MIN_WIDTH=120）。

**整块内边距 = 0x1a = 26 px** 是原版的"九宫格 + 文字内缩"总量：结合 §3.1 的结论（皮肤帧厚 3 px、
引擎不加额外 padding），这 26 px 是选择支对象的固定内缩，而不是皮肤帧厚。仓内 `PADDING=14`
（两侧共 28）与它接近但不相等 → §3-1 的"未取到"项现在有 A 级数值：**26**。

**文本基线偏移 = 2 + (DAT_0084b264<<2)/10**（`004c3fa0.c:25-28`）：

```c
*(float *)(obj + 0x54) = (float)((*(int *)(obj + 0x180) + 2 + (DAT_0084b264 << 2) / 10) * DAT_0084b248);
*(float *)(obj + 0x58) = (float)((*(int *)(obj + 0x184) + 2 + (DAT_0084b264 << 2) / 10) * DAT_0084b248);
```

选择支对象的绘制原点（`obj+0x180/0x184`）到文字原点再加 `2 + 4*fontbase/10`。
本作 1024x576 下若 `DAT_0084b264 = 0x28 (40)` 则 = 2+16 = **18 px**。

### 5.5 【关键】原版面板锚点不读 Sys3/Sys4，且没有越界回退（A 级）

`004c3fa0_FUN_004c3fa0.c:9-24`：

```c
if (DAT_00a18a50 == -1)   /* = obj + 0x8d8 */
    *(int *)(obj + 0x180) = DAT_0084b264 * 10 - *(int *)(obj + 0x188) / 2;
else
    *(int *)(obj + 0x180) = DAT_00a18a50 - *(int *)(obj + 0x188) / 2;

```

- `DAT_00a18a50/54` 不是独立的全局变量，而是选择支窗口对象 `DAT_00a18178` 的
  **+0x8d8 / +0x8dc 字段**（0xa18178+0x8d8 = 0xa18a50，算过地址）。而这两个字段正是
  `FUN_0043e5f0` case 3 / case 4 的默认值（`0043e5f0_FUN_0043e5f0.c:56-72`）：
  `+0x8d8 默认 = DAT_0084b264 * 10`，`+0x8dc 默认 = 0xaa / DAT_0084b248`。
- 全库 grep：`004c3fa0` 是**唯一**读写这两个字段的地方，没有任何代码把它们设成非 -1
  以外——它们由 `FUN_0043e5f0` 的默认值/脚本 opcode 写入，而本作数据里没有任何脚本
  写选择支窗口配置（`scan_sys.py` 与全 CommonEvent 扫描只发现 Sys3/Sys4 = -1000 那一处）。
- **结论：原版 102 面板的落点 = (fontbase*10 - w/2, 0xaa/scale - h/2)，即默认在
  (400, 170) 附近（1024x576，fontbase=40）居中/居中，和 Sys3/Sys4 无关**。Sys3/Sys4 是
  **消息/选项共用窗口** 的位置变量（CE63 写 512/192），而 102 的引擎面板用的是它自己的对象字段。
- **没有越界判断**：整个 `004c3fa0` 只有 `== -1` 分支，没有 `<0 || 屏宽<x` 的
  回退；`004c35c0` 里出现的屏幕边界只用于**鼠标命中哪一行**，不改面板坐标。
  ⇒ 原版策略是「**按锚点原样画，越界即被屏幕裁剪**」，既不是"完全越界才居中"，也不是
  "部分越界回退"，也不是"贴边夹取"。

### 5.6 对仓内的结论（重要）

1. 仓内 `choice.rs:180` 的"完全屏外→居中"回退在原版**不存在**（A 级否定证据：整条
   102 链路里没有任何面板坐标回退）。原版是"画到屏外就看不见"，这正是 CE42 标题用
   (-1000,-1000) 隐藏引擎菜单的机制。
2. 仓内的**锚点来源**（Sys3/Sys4）也与原版不同：原版 102 面板用对象字段 +0x8d8/+0x8dc，
   默认固定为 (fontbase*10, 0xaa/scale)，**不是** Sys3/Sys4。若仓内改成按原版锚点，
   标题菜单会真的出现在屏幕内 —— 与实机标题（无灰框）矛盾。因此两个可能：
   (a) 原版 102 面板在标题这一处因为 `DAT_00a14038` 等条件根本没画；(b) 该对象字段
   在运行期被别的路径改过。**这条没有闭合，标注为 C 级待实测**（见 §7.1）。
3. 仓内 `PADDING=14` 对应原版 26 px 总量的下半截；`LINE_HEIGHT=30` 在原版里
   **没有**对应常量（原版行距 = 选项自带的高度 + 26，见 `004c3d20` 的 `0x18c`
   计算），这也是 C 级待确认。

## 6 §3-7 超宽选项（仅布局侧）

- **原版（A 级）**：面板宽 `= 最宽选项宽 + 0x1a`，**没有上限、没有截断、没有强制换行**
  （`004c3d20_FUN_004c3d20.c:59-72`，见 §5.4）。选项之间的行距也不是常量：面板高由
  `最后一条的宽/高 + 0x1a` 决定（`004c3d20.c:73-77`）。超宽时面板直接超出屏宽，靠 blit 裁剪。
- **脚本侧旁证（B 级）**：万能窗口 CE64 的默认宽 `32*rateX` = 整屏宽（`ce64.txt`：
  `self24 = 32*rateX`、`self25 = 24*rateY`），说明"顶着屏幕宽"是允许的用法。
- **仓内**：`choice.rs:112-117` `width = (widest + marker + 2*PADDING + SLACK).max(MIN_WIDTH)`，
  无上限、无截断 —— 与原版"不截断"一致；超宽时同样伸出屏外被裁剪。
- **差异**：宽度加数不同（原版 `+26`；仓内 `+30 marker +28 padding +4 slack = +62`），
  `MIN_WIDTH=120` 与原版无关（原版宽度按文本量算，单字符选项的面板会明显更窄）。
- 文本侧（行内截断/换行）归 task-3 (TEXT_METRICS.md)，此处不下结论。
