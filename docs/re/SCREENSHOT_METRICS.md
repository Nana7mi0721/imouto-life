# 实机截图度量 — 行距、选项面板与光标（2026-11-02）

本报告把 RE（`docs/re/TEXT_METRICS.md`、`LAYOUT_METRICS.md`）给出的**公式**落到**本作实机像素**上。
反编译给出的是"引擎怎么算"，这里是"本作数据下算出多少"：Game.dat 的基准字号 16、文本行距 6、
选择支行距 14，配上 1024×576 的 1.0 缩放，得到下面这些数。

## 1 素材与缩放标定

`prt sc/` 下 34 张 PNG 全部是**窗口截图**，不是 1024×576 原生帧：宽度 1532–1540、高 855–869，
即客户区被系统缩放 ≈1.5×。换算前必须先标定缩放，再用"字号 = 20"这个已知量反验：

| 图 | 文件 | 原始尺寸 | 标定缩放 | 依据 |
|---|---|---|---|---|
| 89EF | `{89EF6522-CC5B-42B1-AFDE-DC814C6713E4}.png` | 1532×862 | **1.4961** | 全角字 advance 实测 30.1 px / 20 = 1.505；同图消息行距 34.364 / 1.4961 = 22.97 |
| EE37 | `{EE3763D0-...}.png` | 1537×865 | **1.5010** | 全角 advance 30.08 / 20 |

两张图的缩放各自标定，不做跨图平均。文字尺寸由**墨迹宽度**与**全角 advance**双重确认：
全角字在 Sys8=20 时 advance 恰为 20，实测 30.1/1.4961 = 20.12、30.08/1.5010 = 20.08。

## 2 消息窗（opcode 101）行距

89EF 底部三行消息，墨迹带（屏幕像素）[741,769]、[776,803]、[810,837]，亚像素上沿
742.64 / 777.44 / 811.37；三种独立方法量的行距：

| 方法 | 屏幕 pitch | 换算到逻辑 |
|---|---|---|
| 墨迹带上沿最小二乘 | 34.364 | **22.97** |
| 墨迹质心 | 34.194 | 22.86 |
| 行剖面互相关 | 34.543 | 23.09 |

**结论：行距 = 23.0 px = Sys8(20) + 3**，其中 3 = `trunc(6 × min(16,32)/32)`。
这正好验证 RE 的 `line_pitch = 本行字号 + trunc(行距配置 × min(基准字号,32)/32)`
（Game.dat u8[11]=6、u8[0]=16）。仓内 `message.rs` 原先是 `font+6`（=26），只在基准字号 ≥32 时才是原版值，
现已改为 `font+3`。

## 3 选择支面板（opcode 102）

### 3.1 89EF：四行提示

- 外框亮边（1 px 灰线）：物理 x 641.95…875.55、y 345.95…516.55 → 逻辑 **x 427.3…584.0、y 230.0…344.7**
- 面板 **156.1 × 114.0**；行墨迹带物理 359–386 / 400–426 / 440–466 / 480–507
- 行距：上沿最小二乘 27.18、质心 26.94 → **27.0 = 20 + trunc(14×16/32)=7**
- 最宽行墨迹 138.4；边框→首字墨迹 8.05；高亮条（光标）物理 h=30 → 逻辑 **20.05**，
  左右内缩 6.7 / 5.0

高度模型 `H = (n−1)×pitch + 33`（即 6 + n×pitch）对 4 行给 3×27+33 = 114.0，与实测一致。

### 3.2 EE37：五行行动菜单（确认也是 102 面板）

- 精修后外框逻辑宽 **161.8**、高 **140.7**；行距 **26.88**；最宽行墨迹 138.6；边框→墨迹内缩 **7.85**
- 高度模型：4×26.88+33 = 140.5 ✓（= 140.7）

四条独立判据确认它不是脚本 `CE64` 万能窗口，而是同一套 `102` 引擎面板：

1. 行距 26.88 与 89EF 的 27.18 只差 0.3 px —— 同一个常量 27。脚本自画的窗口不可能碰巧给出同一 pitch。
2. 左内缩 7.85 与 89EF 的 8.09 同落 `2+(16<<2)/10 = 8`，是引擎文本原点公式。
3. 高亮条高度两图都 20.0 px（= 字号+1），条内亮度 EE 91 / 89EF 79，是引擎选中行条。
4. 高度经验式 `H=(n−1)×pitch+33` 对两图都成立；33 = 26(边框/内边距) + 7(=choice_line_spacing 14 × min(16,32)/32)，只有 base=16 才对得上。

注：EE 在亮场景下比 89EF 多一条外亮带（col 637.5 值 225、col 887 值 200）；内层亮线（218）才与 89EF 的
单亮线（218）同层。两图的 W 一律取内层亮线，同一口径。

### 3.3 宽度加数：与 RE 的 0x1a 不一致，采用实测

RE（`FUN_004c3d20:59-77`，A 级）说面板宽 = 最宽选项 record 宽 + **0x1a = 26 px**。
精修后两张图量得（逻辑 px）：

| | W | 最宽墨迹 T | W−T | 左边框→墨迹 | 右空隙 | 高亮条宽 |
|---|---|---|---|---|---|---|
| 89EF 4 行 | 156.3 | 138.4 | **18.6** | 8.09 | 9.88 | 218.0（屏幕） |
| EE37 5 行 | 161.8 | 138.6 | **23.9** | 7.85 | 15.39 | 223.5（屏幕） |

两个面板的最宽选项**都是 7 个全角字**（advance 140、墨迹 138.4/138.6），差异全部落在右侧；
且选中行高亮条的宽度也同步差同样量（218 → 223.5 屏幕），说明这不是外框测量误差，
而是 EE 的逻辑宽**确实**大 ~5.3 px。

与 RE 的 +26 对比：EE 差 2.1（若把皮肤亮线相对逻辑矩形内缩 ~1 px 算进去，约差 1），
89EF 差 7.4（换成 +19~20 更接近）。可能是 (a) `FUN_004ce990` 返回的 advance 含尾随空格/引号而两串尾字符不同，
(b) 该处 op102 走了带显式宽度的变体。帧层面无法裁决，**宽度常数只能给 B 级**。

落地取舍：**宽 = 最宽 advance + 2×8 = +16**。理由：文本 advance 140 时 +16 给出 156，
与 89EF 的 156.3 只差 0.3 px（精确复现）；而 +26 会给出 166，比两张实测都宽 4~10 px。
内缩 8 有 RE 公式 + 两图墨迹双证。**开放项（B 级）**：EE 那多出的 5.3 px 未解释，
若日后确认是带显式宽度的变体，只需改 `choice.rs::size()` 一处。

### 3.4 行起点与光标

- 首行墨迹上沿距边框 9 px，字形自身 top bearing ≈3 px → 行矩形起点 **y+6**；仓内 `ROW_TOP=6`
- 面板高 = 6 + n×pitch：4 行 6+108 = 114 ✓、5 行 6+135 = 141 ✓
- 光标是**整行高亮框**，不是字形前缀：89EF 第一行、EE37 第三行各有一条 1 px 亮边矩形，
  内缩左右 6.7/5.0、高 20；`work/Data/SystemFile/CursorBase.png` 是 12×12 RGBA
  （外框浅灰渐变、内部暗红 `272222` 全不透明），九宫格 corner=4，与"帧厚 1/3"规则一致。
  于是仓内删掉 `"▶ "` 前缀，改画 CursorBase 九宫格于 `[x+6, row_y, w−12, font_px]`。

## 6 十分之一单位 UI 块（历史测量；存档/读档界面 CE94 / CE131）

> **当前状态（2026-11-13）**：本节记录的 `Screen::ui_scale_for`、`TENTHS_UI`/
> `tenths_block` 与渲染二次 `/10` 补偿已在当前工作区撤销，相关符号不再存在于
> `wolf-game`。下面的坐标模型只用于解释历史截图、旧测试和旧实现，不是现行渲染路径。

依据：实机参考图 `prt sc/{25B8577A-18EA-4AD0-B444-AEE4B94E60FF}.png`（1532x866，scale 1.4961/1.5035）与我们对 `capture --map SampleMapA --event 5` 的离屏实测 + CE94 脚本 dump（`work/out/play_gpu/ce94.txt`）。

### 6.1 面板与槽位几何
- 面板左边白边逻辑 x=46.8、右边 973.9（宽≈927）；体色 (41,45,49)、边框 (216,218,219)。
- 竖直白边逻辑 y=86.5 / 198.2 / 312.6 / 427.7 / 542.1 → **4 个槽**，每槽高≈112。
- 槽1「数据 1」墨迹左沿 x=70.2（≈面板左缘+23）。

### 6.2 x / y / w / h 的不同缩放（历史 tenths 实现）
CE94 pc83-107 先按坐标倍率把槽字段放大，再用 op121 flags=0x10400 对 **x 侧（self22/30/56/70/73）单独 /10**；y/w/h 保持十分之一。因此渲染 tenths block 时：
- **x 已是像素，历史 tenths 渲染层不再除 10**；
- **y、w、h 仍是十分之一，历史 tenths 渲染层除 10**。

历史实测例：槽窗口 12050 `args=[0,9280,1152,1,255,48,864,100,0,0]` → x=48（像素）、
y=864→86.4、w=9280→928、h=1152→115.2。若把 x 也 /10，面板会落到 x=4.8（正是
旧实现修复前整片黑面板左移的根因）。当前代码不执行这层二次缩放。

### 6.3 chapter 分组
历史实现中 `Screen::ui_scale_for` 的分组键必须是 `number/1000`（不是 /100）：
第 4 槽窗口 12110 属 chapter 121，同块只有自己且 y=4320 被 parked 判据排除，
若按 /100 分组会判成 ui=1 而不绘制；归到 12xxx 后槽1（12050，y=864 非 parked）
成为锚点，四槽统一 10x。当前源码已无该函数。

### 6.4 槽框与光标皮肤
`SystemFile/WindowBase_amania.png`（18×18，体色 0x1F2425 α223、白边 0xf2f3f3）作槽面板；`SystemFile/CursorBase.png`（12×12）作槽框。两者都须用**空心九宫格**（`crates/wolf-game/src/window.rs` 的 `nine_slice_frame`，去掉中心填充）；否则 CursorBase 会把整个槽铺成不透明黑块。

### 6.5 空槽文本与 DB 句柄
CE94 pc319 `179 self[16]` 按队伍人数循环，离线 capture 无真实存档时会误入并画「000000」零值串（真实游戏读到干净存档 self[16]=0 不画，属数据层依赖）。槽标签文本里的未解析字符串槽存的是 DB 值句柄（`1_100_000_000 + row*100 + col`），`crates/wolf-vm/src/text.rs` 的 `parse_escape`（SelfVar 分支）已识别 `MagicKind::DbCell` 并返回空串，避免把九位地址（如 1100001204）印到屏幕。


### 6.6 全屏渐变是黑色阴影，不是白色遮罩（背景发黄的根因）
CE94 pc153 画出全屏 `pic 12000 file "<GRADY-779-111>"`（window 1024x576、tone 默认中性 100%）。`crates/wolf-game/src/sysgraphic.rs` 原先把所有系统图形都合成**白色**纹理再乘 picture tone，于是这条 0.779→0.111 alpha 的渐变把下层房间**提亮**：对 SampleMapA 的米黄地面即得到实机截图中的亮黄背景 (255,244,217)。

实测参考图面板外背景是中性偏暗的卧室：逻辑 (30,300)≈(25,25,31)、(760,300)≈(67,67,67)、(30,800)≈(42,42,46)。若按白 0.78 alpha 覆盖，任何合理房间色都会被抬到 ≥190，与该测量值矛盾；按**黑**同 alpha 覆盖则吻合（底层色 55~150 时落在 25~70）。

全量扫描 `150` 的 38 条渐变绘制（`cargo run -p wolf-format --example dump_event -- scan work/Data/BasicData/CommonEvent.dat 0`）确认它们只出现在商店/菜单/角色/装备/存档/读档/系统/上部状态/战斗等 **UI 与战斗背景**，全部用于压暗场景，且 tone 一律中性白——所以黑纹理是唯一自洽解释。

修复：`crates/wolf-game/src/sysgraphic.rs::render` 的 `Shape::GradX/GradY` 改为填充 `[0,0,0,alpha]`（其余 `<SQUARE>/<SQUARE>FRAME/<LINE>/<CIRCLE>/<TRI-*>` 仍为白纹理、由 tone 上色）。验证：`capture --map SampleMapA --event 5` 背景由 (255,244,217) 变暗为 (86,75,48)（底层米黄地面被压暗）；标题/开机截帧与修复前逐字节相同（渐变只用在这些界面帧）。

### 6.7 HUD / 普通文本的字重与垂直基线（2026-11-03 实测）
- 字体：`Game.dat` 的 `Microsoft YaHei UI Bold`（`C:\Windows\Fonts\msyhbd.ttc`，唯一 face 为 weight 700）。cosmic-text 若按默认 weight 400 请求，会跳过主 face 退到 `seguisym.ttf`，其 digit advance=0.5391em：24px `19:30` 行宽只有 56.95px（glyph 全来自 fallback）。
- 修复后（weight 700）：24px `19:30` 行宽 66.06px，墨迹 x36..98/y11..28（参考 x37..99/y11..28，宽 63）；`持有金钱` 宽 159（参考158）；`周一` 宽34。
- 普通 text picture（HUD、对话等）需在 half-leading 抬升后再下移 **4px**：
  `textpic::PLAIN_TEXT_TOP_OFFSET`。存档槽等原生 `12xxx` UI 标签不加此偏移，
  保持 regular weight 400；当前代码以 `Game::uses_regular_ui_text(number)` 的
  `12000..13000` 范围选择这一样式，而不是 tenths 的 `ui_scale_for`。存档 data
  墨迹 x71..121/宽51（参考 x68..118/宽51），time 宽34~35（参考37，受 LANCZOS
  阈值差 2px）。
- 视觉回归：`day_command` nonblack 532756→533165，`hud` 554374→554868；`title/map_idle/saveui` 不变。

### 6.8 HUD ASCII 空格按 0.5 em 度量（2026-11-03 实测）
