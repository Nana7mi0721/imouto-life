## 1 §3-4 行距：原版是「字号×倍率 + 配置行距×基准字号的 1/32 比例项」

### 原版行为（已定案，公式层面）

文本渲染主函数 **FUN_00494480** 的换行分支（`00494480_FUN_00494480.c:443-547`）在遇到 `'\n'` 时：

1. `x = 0`（`:444`）。
2. **基础步进**：`y += local_98 * (param_1+0x100) / 2`（`:451-452`）。
   - `local_98` = 本行内出现过的最大字号（`:449`, `:527-530`, `:551-553`）。
   - `param_1+0x74` = 经 `FUN_0049b440` 钳制后的字号（`:264-267`，钳制规则见 §5）。
   - `param_1+0x100` = `DAT_0084b248 << 1`（`:295`）；当 `DAT_00a1928c==200` 时再 `/2`（`:303-306`）。
   - 即 **基础步进 = 本行最大字号 × S**。
3. **额外行距**（仅当 `param_1[0xe0]==0`，普通窗口文本；且 `param_1+100` 的行计数 < `FUN_004ce080()`，即不在最后一行之后再加）：`:456-487`

   ```
   y += (((int)(*DAT_00a166a0 * local_710) >> 5) * (param_1+0x100)) / 2
   local_710 = *DAT_00a16674 < 0x21 ? *DAT_00a16674 : 0x20
   ```

   即 **额外行距 = 行距配置 × min(基准字号, 32) / 32 × S**（`>>5` 是算术右移 5，配 `+ (x>>31 & 31)` 的向零取整）。
   第二分支 `:489-525`（`param_1[0xe0] != 0`）改用 `*DAT_00a166a4`，公式相同。**[推断]** 这两个配置分别对应 `Game.dat` u8[11]=`text_line_spacing`=6 与 u8[12]=`choice_line_spacing`=14（仓内 `gamedat.rs:272,278` 的命名），但哪条指针指向哪个字段尚未在 dump 里闭合。

**合并结论**：

```
line_pitch = max_font_on_line * S + trunc(line_spacing_cfg * min(base_font_cfg, 32) / 32) * S
```

- 行距**比例项只跟“基准字号配置”挂钩，不跟当前行的字号挂钩**。行内 `\f[40]` 放大只抬高基础步进（本行最大字号），不抬高那 6 px。
- 本作 `Game.dat`：u8[11] = **6**（仓内 `gamedat.rs:272 text_line_spacing`），u8[0] = **16**（基准字号候选，见 §0.1）。

### 仓内实现

`crates/wolf-game/src/message.rs:43` `LINE_GAP=6.0`；`:122-124` `line_height(font) = font + 6`；
`:318` / `:584` 每行 `y += line_height(该行最高字号)`。

### 差异

| 项 | 原版 | 仓内 | 判定 |
|---|---|---|---|
| 基础步进 | 本行最大字号 × S | 字号 + 6 | 等价于把配置行距折进了字号 |
| 行距项 | `6 × min(base,32)/32`，与当前字号无关 | 恒 6 | **不等价**：base=16 时原版是 3；`\f[40]` 时仓内变 46，原版仍是 20+6（base≥32 时） |
| 缩放 | ×S | 无倍率概念 | 1024×576 下 S=1，暂无差异 |

**+6 是否有依据？** 有：`Game.dat` 的 `text_line_spacing` 确实是 6，而且原版在 `min(base,32)=32` 时正好把 6 px 加到行距上。但 **+6 不是常量式的“字号+6”**：
- 若运行时基准字号 = 16（`Game.dat` u8[0]），原版行距项 = `6*16/32 = 3`，Sys8=20 时行距应为 **23**，不是 26。
- 若运行时基准字号 = 32/40（FUN_00469820 的三个分支暗示“文字尺寸”是可切换设置 16/32/40），则行距项 = 6，Sys8=20 时 **26**，与仓内注释的 [已实测] 26 吻合。

⇒ **部分**。公式已定案；`*DAT_00a16674` 的运行时值（16 还是 32/40）未定，因为该指针是 BSS 指针、其赋值点不在 4375 个 ≥64B 函数的 dump 里（见 §6 复现）。建议实机分别用 `\f[20]`/`\f[40]`/`\f[14]` 量行距：原版应呈 `font + 6`（base≥32）而非 `1.3×font`。

### 关于 `FUN_004325e0:869` 的 `DAT_0084b264 * 6 * DAT_0084b248`

**这条不是消息窗行距**，而是消息历史/翻页器（log pager）的**滚动步进**：

- `:868-875`：翻页键后 `DAT_00a1b154 += min(DAT_0084b264*6*S, DAT_00a1b154 + local_2c - local_20)`，再递归重绘（`:878`）。`DAT_00a1b154` 是**累计滚动偏移**（所有绘制 y 都减它，如 `:825`），`local_2c = 0x294 = 660` 是页高（`:100`）。
- 该函数自己的行步进是 `local_18 = 0xdc = 220`（`:99`, `:208`, `:249`），逐字 x 步进是 **固定 10 px**（`local_24 = 10`，`:101`, `:173`, `:230`, `:364`）——不是 GDI 字宽，说明它是**等宽排版的历史/调试列表**，不是 101 消息窗渲染器。
- `6 × DAT_0084b264 × S` 的量纲是“6 个文字尺寸单位”（40/32/16 ⇒ 240/192/96 px），与 220 的行步进和 26 的行距都对不上。

**结论：不能用它推导 101 消息窗的 +6；真正管行距的是 FUN_00494480 §1 的公式。**（已定案）

> 交叉印证：`docs/RE_GAME_EXE.md:252` §9.2.4 独立得出“文本渲染器里没有 +6 这类常数、行推进 = 本行最大字号 × 倍率”，与本节的“基础步进”一致；本节补上了它没有展开的**额外行距项**（`:456-525`）。

## 3 §3-5 打字机：原版是**逐帧累加**到 double 水位线，不是 `floor((frames-preroll)*cps/60)`

### 原版行为

**(a) 显示门限**（`00494480_FUN_00494480.c:355-367`）：

```
if (param_2 && local_89 && *(double*)(p+0x88) < (double)(p+0x68) - (double)(p+0xf8))
    *(double*)(p+0x88) = (p+0x68) - (p+0xf8);        // 只升不降
if (param_2 && !local_89) {
    i = round(*(double*)(p+0x88));                    // FUN_004fe844 = x87 浮点取整
    if (i + p+0xf8 < p+0x68) goto LAB_0049accf;       // 还没显示到 → 停止本帧绘制
}
```

- `p+0x88`(double) = **已显示字符数**（水位线）；`p+0x68` = 当前字节下标；`p+0xf8` = 已消耗的标记字符数。
- `local_89` 由控制码 **0x0b** 清零（`:1850-1852`，即“暂停标记”），参数 `param_2` = “正在打字”标志。
- 水位线每次被抬到当前字符（`:1834-1837` 同款），**单调不减**。

**(b) 每帧推进**（`004c2d50_FUN_004c2d50.c:10-25`）：

```
if (!p[0xe2] && p+0xe8 < 1) {
    p+0x88 = min( (DAT_0084b244 * p+0x80) / 30.0 + p+0x88 , 5.0e7 );   // K=30 见下
}
if (p+0xe8 > 0) p+0xe8 -= DAT_0084b244;      // 计数以“帧片”为单位
```

常量已从 Game.exe 数据段读出（`work/out/text_metrics/consts.py`）：
- `_DAT_00829888 = 30.0`（除数）
- `_DAT_007d1ea8 = 5.0e7`（上限，等于无限）
- `_DAT_00802e18 = 1.0`（下限）
- `DAT_0084b244 = 60/fps`（60fps 时为 1）

⇒ **每帧增量 = (60/fps) × speed / 30 = speed / 30（60fps）**，即每秒 **speed/2** 个字符。
若 `p+0x80` 直接存 Sys9（字符/秒），原版实际速率是 **2 × Sys9**；仓内是 **Sys9/60 每帧 = Sys9 每秒**，慢一半。

**这个 2× 有两条解释，尚未区分：**
(a) 该更新函数每帧只跑一次（已确认：主循环 `004c1bb0_FUN_004c1bb0.c:335` 每帧无条件调 `FUN_004c2ae0`，后者 `:10-11` 调 `FUN_004c2d50`；另一路径 `004c35c0_FUN_004c35c0.c:25`），所以 30 就是“每帧 1/30 秒”，原版确实 2×Sys9；
(b) `p+0x80` 存的是 **2×字符/秒**（`\f` 代码/op150 参数在别处已乘 2），则 30 只是形式上的 1/30 秒。

(a)(b) 都要求 `p+0x80` 与 Sys9 的绑定点，**该点不在 4375 个 ≥64B 函数里**（`*DAT_00a16674/00a166a0/00a166a4/00a18ad8/00a18adc` 全是 BSS 指针，赋值点缺失，见 §6）。

**(c) `p+0x80`（每秒速度）的来源**：
- 文本对象构造默认 = `_DAT_007d1100 = 240.0`（`0049bfe0_FUN_0049bfe0.c:29-30`）。
- 消息内控制码 0x0c（`\f`/速度码）可覆盖：`00494480_FUN_00494480.c:1853-1886`，解析 3 字节值，`<1` 取 1，`0/0xffff` 取 `DAT_00a18adc`（默认速度）。
- 图片文本（op150 文本）路径：`004c2e40_FUN_004c2e40.c:9` `p+0x80 = _DAT_00a18ad8`。

**未找到**：Sys9 → `p+0x80` 的直接写入点（101 消息窗的 per-message setup 函数还没定位）。⇒ 该条 **部分**。

**(d) preroll / Sys10**：
- `p+0xe8` 是 `DAT_0084b244` 单位的倒计时，`>0` 时**暂停推进水位线**（上 (b) 分支）；`p+0xe2` 是“等待输入/暂停”标志。
- 消息内控制码 **0x0e**（`:1887-1892`）：`p+0xe4 = 下标+1; p+0xe8 = 0x10`（16 帧片）——即**行内等待 16 帧**。
- 控制码 **0x0f**（`:1893-1901`）：置 `p+0xec = 下标`、`p+0xe2 = 1`（等待玩家按键）。
- 这三个字段里**没有“整条消息起手前先等 N 帧”的减法公式**；`(frames - preroll)` 的语义在 dump 里没有对应实现。

### 仓内实现

`crates/wolf-game/src/message.rs:268-279`：

```
if cps <= 0 { None }
if frames < preroll { Some(0) }
floor((frames - preroll) * cps / 60)
```

cps=Sys9（boot 500），preroll=Sys10（boot 9）。

### 差异

| 项 | 原版 | 仓内 | 判定 |
|---|---|---|---|
| 推进方式 | 每帧 `+= (60/fps)*speed/30`，double 累加、单调 | 由总帧数一次算 `floor(frames*cps/60)` | 数值上近似，但原版速率是 **2×**（除数 30 而非 60） |
| 初始延迟 | 用 `p+0xe8` 帧片倒计时（消息内 `\!` 等码），**不**从 Sys10 减 | `frames - preroll`，Sys10=9 → 首 9 帧无字 | 语义不同；Sys10 是否进入该字段**未找到** |
| 60fps 假设 | 用 `DAT_0084b244=60/fps` 归一，可变帧率正确 | 硬编码 60 | 本作 60fps 下无差 |

⇒ **部分**：显示门限与累加公式已定案（`+0x88`, `/30`）；**除数 30（=2×Sys9）和 Sys10 的真实注入点是两条需实测项**。
建议实测：把 Sys9 设成 30 与 60，逐帧数首 10 个字，比较“每帧 1 字 vs 每帧 2 字”。

## 4 §3-7 超宽选项 / 超宽文本：**仍待实测（TODO）**，但已排除“渲染器内部截断”

### 已确认（可缩小范围）

1. **FUN_00494480 自身不做水平裁剪**：它按调用方给的字符串逐字画，x 单调累加（`:834-837`），没有“超过某个宽度就停”的比较；绘制走 DxLib 文本 API（`FUN_00540340`/`00540540`/`005406b0`），本函数内部没有 SetDrawArea/裁剪矩形调用。⇒ 若发生截断，只可能发生在**调用方**（op102 面板设置 DxLib 全局裁剪区）或“构造字符串时截断”；渲染器本身不截。
2. **没有换行参数**：渲染器只认字符串里的 `'\n'`（`:443`）；超宽文本不会自动折行。仓内 `choice.rs` 也是一行一项、不折行。
3. **字体句柄缓存 / 字号上限 400**：`0049adc0_FUN_0049adc0.c` 是字体的**懒创建缓存**（参数是字体槽 0..4、字号、样式；`FUN_00530810` 建 DxLib 字体句柄，失败时打 "This font was not generable."），入口把字号夹到 400：

   ```
   if ((int)param_3 < 0x191) local_30 = param_3; else local_30 = 400;
   ```

4. **面板测宽 helper 存在**：`004a1c60_FUN_004a1c60.c:12-33` 遍历一个字符串列表，取“最长行宽”和“总高”，然后由调用方写回 `p+0x70/p+0x72`（`004a1150_FUN_004a1150.c:190-202`）——这是“窗口按文本内容自适应尺寸”的机制，不是截断。若 op102 面板也用同一机制，超宽选项只会把面板撑宽，而不会截断/滚动/折行。**该推断尚未在 op102 调用点验证。**

### 未定案 / 下一步

- 还没定位 **op102 选择面板绘制函数**。本轮试过但失败的入口：源码字符串 `"Selection list =>"`（exe VA 0x7c7588）只被 `FUN_00401c50`（通用调试/字符串 helper）引用；`WindowBase`/`SystemFile/Window` 在 exe 里没有 ASCII 字面量（皮肤路径来自 System DB）；`FUN_00432540`（九宫格框绘制）只被 `004325e0` 调用，是进度条不是面板。
- 建议用 Ghidra 新反编译（需先和 lead 报备项目锁）：
  1. 找 VM 的 opcode 分发表（op101/102 相邻），从 op102 handler 跟到面板绘制；
  2. 或在 `0043f460/0043e5f0`（System DB type10 读值）附近找“窗口显示”配置的消费点。
- 实测更便宜：构造 2 个选项，其文本宽度分别为 ~900px 与 ~1100px（超 1024 屏宽），截原版图看：
  - 面板左边界/右边界是否出屏（=撑宽，不处理）；
  - 文本是否被切掉最后一个字（=截断）；
  - 是否出现第二行（=强制换行）；
  - 是否有横向滚动（几乎不可能）。

**判定：仍待实测。仓内“不处理超宽”与现有静态证据不冲突（渲染器无裁剪、无换行），但无法证明原版就是不处理。**

   - `DAT_0084b248 == 2`（320×240 逻辑屏）：窗口高度 `*DAT_00a16714 < 0xdc(220)` 时字号上限 **0x50=80**、下限 **2**；否则下限 **2**、上限 **200**（`:17-73`）。另有修正表 4→3、5→6、9→8、0xb→10、0xd→0xc（`:49-66`，仅当 `DAT_00a14120<2`）。
